What kind of RAG?

Local hybrid retrieval, with model-assisted compression and relevance revalidation. A vector search finds meaning; a lexical search helps find exact terms. The output is context, not a generated solution.

01 / RETRIEVAL DESIGN

Meaning and exact values work together.

Dense vectors capture similarity in meaning. Lexical retrieval preserves a path to exact error codes and selected identifiers. Logchat combines ranks using reciprocal rank fusion, then checks relevance.

02 / CONTEXT DESIGN

A useful memory needs its boundaries.

Keep project, environment, source, timestamps, exact metrics and loss notes attached. Admit candidates across comparison cells under bounded budgets. A score alone cannot tell you what the context proves.

03 / EVALUATION

Running is different from retrieving well.

Measure candidate precision and recall, ranking quality, selected-context relevance, and no-evidence behavior. Check compression loss and summary facts separately. Passing software tests is not a semantic quality certificate.

What is implemented in the native candidate

  • Explicit local capture into one semantic core.
  • One selected Ollama generation model for grouping, summaries and relevance; a separate embedding capability.
  • Compact memories, scoped hybrid retrieval and supporting-memory inspection.
  • Durable processing, bounded retries and restart recovery.
  • Context-only delivery through CLI, API, browser and project-bound MCP.

Finding memories, filtering them, and reranking them

Our current RAG uses hybrid ranking followed by a model-based relevance filter. A cross-encoder would be a new, separately configured scoring component—not something we already run.

Ranking: which comes first?

Vector search encodes the query and finds nearby stored embeddings. Keyword search finds matching terms. Reciprocal Rank Fusion (RRF) merges their ranked lists: score = Σ 1 / (constant + rank). It combines rank positions rather than adding incompatible raw scores. It is not a probability of correctness. RRF reference.

Filtering: which should stay?

Our shared generation model reads the question and a bounded set of candidate memories, then selects supporting references with a reason and confidence. Code checks those references and preserves the existing order within each comparison cell. It can remove noise, but it cannot move a stronger memory above another retained memory. Its confidence is uncalibrated.

Reranking: score every pair

A cross-encoder reads the query and each candidate together, attending across both texts, and produces a relevance score. Sorting these scores changes candidate order. Unlike independently computed embeddings, this pair-specific computation happens at query time. Apply it to a shortlist, not the entire archive. Score ranges depend on the model; they are not automatically probabilities. Retrieve and rerank reference.

Stage 1 of 4

Neither approach verifies summary truth, establishes a root cause, restores an omitted identifier, or recovers a memory that never reached the candidate pool.

Model-based filtering fits these scenarios

  • Several candidates mention authentication, but only some address session renewal.
  • An agent asks for a particular context and needs irrelevant memories excluded.
  • Comparisons across environments need evidence selected separately without dropping a whole comparison cell.

It uses our existing shared generation profile. Cost includes prompt length, generation time and competition with ingestion for the same local model.

A cross-encoder fits these scenarios

  • The useful memory is in the shortlist but falls below the context limit.
  • Many near-duplicate errors share words; query–candidate interaction may distinguish renewal from login or a successful recovery.
  • Repeated evaluation shows ranking errors and a candidate scorer improves top results within the latency budget.

It adds model loading, memory use and query-time inference. A general search reranker must be evaluated on our log vocabulary, identifiers and time comparisons.

Where each engineering component belongs

The query path is scope → vector + lexical retrieval → RRF → bounded admission → relevance filter → context. A proposed reranker belongs after RRF and before final context selection. It must score only authorized candidates and fit inside the admission budget.

1. Capture and durable processing — get events into one core

Adapters normalize source identity, event time and measurements. File cursors and delivery acknowledgements control replay. Durable jobs, retry limits and explicit gaps handle outages. These components manage delivery; they do not decide relevance. Source integration should never replace the RAG pipeline.

2. Group and summarize — preserve useful information before retrieval

The shared generation model groups related records and writes compact context. Selected exact fields, measurements, scope and loss notes accompany prose. Summary-only storage saves space, but a discarded detail cannot be recovered by a better reranker. Evaluate identifier preservation and summary accuracy separately. A reranker should see sufficient retained fields, not just a vague sentence.

3. Embed and index — make meaning and exact terms searchable

The embedding capability converts compact memories to vectors; the native store uses SQLite with sqlite-vec and a lexical index. Embeddings and generation serve different tasks. Keep embedding model identity and revision attached to the index; changing the embedding space requires re-embedding or a separately versioned index. Publishing a memory and its search representation must avoid partly indexed evidence.

4. Scope and retrieve — protect boundaries and maximize recall

Apply project, environment, source and time constraints before model evaluation. Retrieve a bounded shortlist through both search paths. Recall@K measures how much labeled relevant evidence reaches this pool. If a needed chunk is missing here, first inspect ingestion, compression, scope and candidate depth. A later scoring stage cannot manufacture it.

5. Fuse ranks and admit candidates — control disagreement and cost

RRF favors memories appearing high in either or both lists without treating cosine and lexical scores as the same scale. Admission then limits candidates, bytes and characters while preserving comparison-cell coverage. Candidate depth and context depth are separate controls: fetching more evidence need not mean returning it all. Log budget omissions explicitly.

6. Filter today; evaluate reranking as a separate capability

Our remapper validates the model’s selected reference IDs and confidence threshold. It does not use provider output order to reorder evidence. Invalid responses or unavailable models produce explicit gaps, not silently “validated” candidates. A future scorer would return {memory_id, score, model_revision}; code would check finite scores, exact candidate membership and deterministic ties, then rank within cells. Keep original fusion scores and selection provenance distinct.

This would be a deliberate architecture change: the cross-encoder needs a separate scoring capability, like embeddings have their own capability. Keep configuration centralized; do not silently replace the selected generation model or introduce an automatic fallback. Benchmark replacing the expensive filter versus placing a scorer before it; avoid paying for both without demonstrated benefit.

7. Package context — evidence for another agent

Return selected summaries, supporting memory IDs, retained fields, exact metrics, time bounds, model provenance and gaps. Logchat supplies context; the requesting agent decides what to answer. Relevance scores cannot justify causal claims. A retained section’s counts also cannot automatically become counts for one named user inside that section.

Which path should we take?

Keep hybrid retrieval plus filtering as our release baseline. Build a labeled retrieval evaluation before adding a reranker. This is an engineering recommendation based on the current architecture, not a measured claim that retrieval quality is sufficient for every workload.

Now: establish sufficiency

The current path provides semantic and exact-term retrieval, bounded evidence selection and no extra scoring model to install. It is sufficient for a scoped local release only if representative queries meet agreed quality and latency targets. Software regression and capture tests establish functional behavior; they do not establish Precision@K or ranking quality.

Next: identify the failure

Missing from candidates? Improve recall, chunk content or scope. Present but ranked too low? Test a reranker. Relevant candidates incorrectly rejected? Tune or replace the filter. Search too slow? Profile the index. Ingestion falling behind? Tune scheduling and inference concurrency. More stored logs alone do not identify which change is needed.

Then: promote measured improvements

Compare RRF alone, RRF plus our filter, RRF plus a cross-encoder, and a combined path on the same held-out queries. Keep a change only when it improves context quality without unacceptable latency, memory use, empty results or comparison-cell omissions. Set workload-specific targets; there is no universal chunk-count or precision threshold that forces reranking.

How we scale, in order

  1. Create ground truth. Label relevant memories for paraphrases, exact emails/codes, near-duplicates, multiple environments, time ranges and no-evidence queries. Include difficult negatives and queries whose needed details were lost during compression.
  2. Measure each boundary. Track candidate Recall@K, returned Precision@K, nDCG@K (graded ranking quality), MRR (first relevant result), empty-result correctness and retained-field accuracy. Record p50/p95 latency, queue age, input bytes, model time and peak RAM. Cross-encoder evaluation tools.
  3. Run a bounded scoring experiment. Start with a small candidate shortlist, batch query–memory pairs, cap tokens and timeout, and measure on the actual CPU/GPU. Numbers such as 20–50 candidates are experiment settings, not current defaults or guaranteed optimal values. Long summaries may truncate the decisive field: test this explicitly.
  4. Preserve contracts. Scope candidates first; deduplicate IDs; score and retain coverage within comparison cells. Treat log text as data, not instructions. Version the scorer, prompt and index; report failures and provenance. Cache only with scope, query, content and model revisions in the key.
  5. Address storage and throughput separately. Batch inference and bound concurrency so queries cannot starve ingestion. If exact vector scans become the measured bottleneck, evaluate an approximate index and its recall tradeoff before changing storage. Compact older memories only with lineage and loss checks; a cross-encoder does not reduce archive size or prove year-scale retention.
  6. Roll out deliberately. Run an opt-in shadow comparison before changing returned context, examine regressions by source and environment, document installation requirements, and keep a reversible configuration. No silent fallback between models.

Still unproven: year-scale footprint, broad log-domain retrieval quality, and cross-encoder gains on our data. This page explains an evaluation plan, not a completed scalability benchmark.
